# Targets: where the docs live and how they show a picture

The rules do not change with the target; only the file layout, the nav manifest, and the image syntax do.
Whatever the target, the **source of the docs lives in the code repository**, so a change and its docs are one
commit and one review.

## Sites

| Generator | Pages | Nav manifest | Config `nav` |
|---|---|---|---|
| Fumadocs (React Router, Next) | `content/docs/` | `meta.json` per folder, `pages` in reading order | `meta.json` |
| MkDocs / Material | `docs/` (`docs_dir`) | `nav:` in `mkdocs.yml` (absent: file order) | `mkdocs` |
| mdBook | `src/` | `src/SUMMARY.md` | `summary` |
| Docusaurus | `docs/` | `sidebars.*` or autogenerated | `none` |
| VitePress / Starlight | the content folder | the config's `sidebar` | `none` |
| Sphinx | the `conf.py` folder | `toctree` directives | `none` |

`none` means the checker skips the nav check; the site's own build is the check (a dead sidebar entry fails a
Docusaurus or Sphinx build). Run the site build in CI either way: it is the cheapest link and syntax check
there is.

**Images on a site.** Keep image paths plain (Fumadocs: `remarkImageOptions: false`), so a component can find
the dark twin beside the light file. A `Figure` component that does it:

```tsx
// both variants in the markup, CSS shows one: no flash on a theme change
<img srcSet={`${src} 2x`} alt={alt} className="dark:hidden" />
<img srcSet={`${dark} 2x`} alt={alt} className="hidden dark:block" />
```

`srcSet` with `2x` and no `src` shows a 2x capture at its 1x size: the picture appears at the size it has in
the app, sharp on a high-density screen, never stretched to the column. MkDocs Material does the same with
`![alt](x.png#only-light)` and `![alt](x.dark.png#only-dark)`.

## A `docs/` folder of markdown

Pages are plain markdown in `docs/`, read on the forge (GitHub, GitLab) or in an editor. An `index.md` or
`README.md` links every page in reading order; set `nav` to `none`, or to `summary` with `docsRoot`'s
`SUMMARY.md` if you keep one. Relative links (`[Exporting](exporting.md)`) resolve on the forge and in the
checker. Images sit in `docs/images/`, referenced relatively.

**Dark mode on GitHub** uses `<picture>`, which GitHub renders in markdown:

```html
<picture>
  <source media="(prefers-color-scheme: dark)" srcset="images/export-menu.dark.png">
  <img src="images/export-menu.png" alt="The Export menu with Format set to CSV" width="640">
</picture>
```

Set `width` to half the capture's pixel width (the 1x size). **GitLab** has no theme switch for markdown
images; use `"themes": ["light"]` there unless a site build also renders the folder.

## A wiki (GitHub or GitLab)

A wiki is a separate git repository (`<repo>.wiki.git`), so editing it by hand breaks the one rule that
matters: the docs land in the same change as the code. Keep the wiki's source in the code repository
(`wiki/`, with `Home.md` and `_Sidebar.md`), check it there, and let CI publish it on the default branch.

- GitHub wiki: pages are flat (folders are flattened on display), names are file names with `-` for spaces,
  links are `[[Page Name]]`, `[[text|Page-Name]]` or `[text](Page-Name)`, the sidebar is `_Sidebar.md`.
- GitLab wiki: folders are kept, links are `[text](folder/page)`, the sidebar is a page named `_sidebar`.
- Config: `"target": "wiki:github"`, `"docsRoot": "wiki"`, `"nav": "sidebar"`, `"frontmatter": []`. The
  checker resolves wiki links by page name anywhere in the folder.

GitHub Actions (the wiki must already have one page, created once in the browser):

```yaml
publish-wiki:
  if: github.ref == 'refs/heads/main'
  runs-on: ubuntu-latest
  permissions: { contents: write }
  steps:
    - uses: actions/checkout@v4
    - run: |
        git clone "https://x-access-token:${{ secrets.GITHUB_TOKEN }}@github.com/${{ github.repository }}.wiki.git" ../wiki
        rsync -a --delete --exclude .git wiki/ ../wiki/
        cd ../wiki && git add -A
        git -c user.name=docs-bot -c user.email=docs-bot@users.noreply.github.com commit -m "docs: sync from ${GITHUB_SHA::8}" || exit 0
        git push
```

GitLab CI (a project access token with `write_repository` in a masked `WIKI_TOKEN` variable):

```yaml
publish-wiki:
  rules: [{ if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH', changes: [wiki/**/*] }]
  script:
    - git clone "https://oauth2:${WIKI_TOKEN}@${CI_SERVER_HOST}/${CI_PROJECT_PATH}.wiki.git" ../wiki
    - rsync -a --delete --exclude .git wiki/ ../wiki/
    - cd ../wiki && git add -A && (git -c user.name=docs-bot -c user.email=docs-bot@example.invalid commit -m "docs: sync from ${CI_COMMIT_SHORT_SHA}" && git push) || true
```

The published wiki is a derived copy: nobody edits it in the browser. Say so on `Home.md`.

## README only

For a small tool, one `README.md` carries what it is, install, a quickstart, and usage. Set `"target":
"readme"`, `"docsRoot": "."`, `"include": ["README.md"]` (so the checker reads that page and not every
`AGENTS.md` in the tree), `"nav": "none"`, `"summary": false` if the README opens with badges, and point each
surface's `pages` at `README.md`. Split into `docs/` when install, quickstart and topics stop fitting on one
screen of contents.

## CI, whatever the target

```yaml
# GitHub Actions
docs-parity:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
      with: { fetch-depth: 0 }
    - run: python3 tools/docs_check.py --changed "origin/${{ github.base_ref || 'main' }}..HEAD" --stale --note "${{ github.event.pull_request.body }}"
```

```yaml
# GitLab CI
docs-parity:
  variables: { GIT_DEPTH: 0 }
  script:
    - python3 tools/docs_check.py --changed "origin/${CI_MERGE_REQUEST_TARGET_BRANCH_NAME:-$CI_DEFAULT_BRANCH}..HEAD" --stale --note "$CI_MERGE_REQUEST_DESCRIPTION"
```

`tools/docs_check.py` is a copy of the plugin's script (one file, stdlib only), so CI needs no plugin install;
refresh the copy when the plugin updates. A full clone matters: `--changed` and `--stale` read history. Any
nonzero exit fails the job; accept a finding in the config, with its why, rather than loosening the job.

# The plugin

Generated by `node scripts/gen-guide.mjs --write` from the catalog, the plugin's manifest, each area's `door.json`, and each route's own description. Do not edit it by hand: the gate fails a copy that has drifted.

Install it with `/plugin install agentic-engineering@agentic-engineering` after `/plugin marketplace add`. A person types one skill, `/agentic-engineering:start-here`, or says what they want in plain words: nothing else of the plugin is in the slash menu. The addresses below are an agent's, which calls an area with the route as the first word of its arguments. A route marked *when you ask for it* is never started on the agent's own.

## agentic-engineering

A dozen plugins list about eighty skills, and a job does not say which one it needs, so this is one plugin: a person types /agentic-engineering:start-here and is asked what they want; an agent calls one of eight areas by name (agents, code, delivery, design, docs, harness, planning, writing); and each area routes to its own procedures, read as documents that cost nothing until one is taken.

## start-here

Use when a person asks what the agentic-engineering plugin offers, which of its areas does a job, or how to begin with it. An agent with a task calls the area whose name fits (agents, code, delivery, design, docs, harness, planning, writing) and does not come here first; ordinary work no area covers needs no skill, this one included. With a person it asks which areas they want, explains each, and hands off to the route that does the work. With the task as its argument, or with nobody to ask, it asks nothing and names the area and route that fit.

The one skill a person types: `/agentic-engineering:start-here [the task, in a sentence]`.

## code

Use on any coding task to build at the simplest rung that holds, reuse before building, cut over-engineering and track debt, and to restructure a repo that has already accreted: a sprawling tree, god-files, shallow coupled modules.

| An agent's address | Started | When |
|---|---|---|
| `/agentic-engineering:code ladder` | by the agent | Build at the first rung that holds: YAGNI, reuse what the repo already has, stdlib, native platform, installed dependency, one line, the minimum that works. Use on any coding task (writing, adding, refactoring, fixing, choosing a dependency) and whenever the user asks for the simplest solution or complains about bloat, boilerplate, or over-engineering. To check what already exists before building use reuse; to audit shortcuts already in the tree use debt. Not for prose. |
| `/agentic-engineering:code reuse <the thing, in plain words>` | by the agent | Before building a component, a utility, a parser, a client, or anything else that sounds like it might already exist, check what this repo and the other checkouts the person has listed already have. Use whenever a task would add a dependency, a UI component, or a capability another module plausibly has, and whenever the ladder reaches rung 2. To offer something back the other way use capture. |
| `/agentic-engineering:code review [repo] [--base <ref>] [--apply]` | by the agent | Hunt over-engineering in the working diff (pass `repo` to widen to the whole tree): review-scan.mjs locates cut candidates deterministically, you judge only the flagged spots, one line per finding with file:line, the cut, and the replacement; `--apply` lands each confirmed cut as its own commit behind validate-or-revert. Use before opening a pull or merge request, or when a diff feels bloated. Correctness bugs and security holes are out of scope here; the ladder is what stops the bloat being written in the first place. |
| `/agentic-engineering:code debt [--write <file>]` | by the agent | Inventory every `debt:` marker in the repo with scripts/debt.mjs, judge whether each deferral still holds, and flag trigger-less markers as rot risk. Use when auditing shortcuts already in the tree, before a release, or when the user asks what debt this repo carries; the ladder route is what writes new markers. |
| `/agentic-engineering:code capture` | by the agent | At the end of a session, find what this work built that another project would want: a component, a repo-agnostic utility, a script, or a pattern worth a plugin. Writes a row in .agents/reuse-opportunities.md for each. Use when wrapping up work that produced something general; reuse is the same question pointed the other way. |
| `/agentic-engineering:code restructure` | by the agent | The whole sweep and the entry point for the other two skills here: organize the tree, split god-files, deepen shallow modules, each stage on a branch behind the repo's own tests with revert on red. Use when the ask is a multi-stage refactor over a repository that has accreted ("optimize this codebase", "decompose these huge files"). Nothing starts until the person has seen the run plan and said yes. For the tree alone use organize; for seams alone use deepen. |
| `/agentic-engineering:code organize` | by the agent | Reorganize a sprawling file tree into a progressive-disclosure layout: plan, history-preserving git mv, reference rewriting, AGENTS.md hubs, verified by the repo's own build. Use when the ask is about the tree alone (the root is a mess, too many top-level files, organize the folder structure, add AGENTS.md hubs to this repo). Nothing moves until the person has approved the plan. To split god-files in the same pass use restructure. |
| `/agentic-engineering:code deepen` | by the agent | Find deepening opportunities in code that already exists: shallow modules, leaky seams, missing adapters, proposed against the project's glossary and its decision records under .agents/. Use when the ask is about architecture ("improve the architecture", consolidate tightly-coupled modules, make this testable) or a seam worth extracting has been spotted. For the file tree use organize; to apply deepenings autonomously behind revert on red use restructure. |

## design

A front end: one system for every repo, a pin, and a check that fails on anything off-system.

## agent-works

Agent workflows rot the same way in every repo: a bloated AGENTS.md, the same rule stated four times, task state in six places, a round of parallel work that lives in one conversation, and no word between sessions sharing one machine. agent-works gives each kind of fact one home under .agents/ with a size budget, checks them with one command (aw doctor), keeps tasks and owed checks on a kanban board the person and the agents share, runs a large goal as child sessions in their own worktrees from that board, guards the files and runs that need it, and coordinates locks, leases and learnings across projects through the aw command line.

Version 1.0.0. [README](../plugins/agent-works/README.md), [changelog](../plugins/agent-works/CHANGELOG.md).

| Skill | Started | When |
|---|---|---|
| `/agent-works:agent-works` | by the agent, or by hand | Use when unsure where an agent-facing fact goes in a repository, or which agent-works skill owns a task. |
| `/agent-works:board [status\|ready\|add\|move\|owe\|settle ...]` | by the agent, or by hand | Use for anything on the kanban board: out-of-scope work to put on it instead of doing it now, what is ready or in progress, moving or planning a card, owing a check this session cannot run, settling one with evidence. |
| `/agent-works:coordinate` | by the agent, or by hand | Use before a heavy job, a timing run or shared use of a GPU on a machine agents share, and to leave a note, claim a shared counter or record a lesson for other sessions. |
| `/agent-works:decisions` | by the agent, or by hand | Use for a hard-to-reverse choice, a new project term, or an agent contract page. |
| `/agent-works:dispatch <card id> [--serial]` | by the agent, or by hand | Use when a card on the board should start: the person approved a parallel set, the orchestrator picked the next ready card, or the kanban pane asked to start one. |
| `/agent-works:doctor` | by the agent, or by hand | Use when AGENTS.md, memory or status bloats, rules repeat, ./docs holds agent files, or a command fails because the machine lacks Node, git or the forge's command line. |
| `/agent-works:guard` | by the agent, or by hand | Use when the agent guard refuses, questions or warns about a command or an edit, or a mistake must not happen again. |
| `/agent-works:hubs` | by the agent, or by hand | Use when adding, moving, renaming or removing a directory, when aw hubs reports a finding, or when a tree needs a new AGENTS.md hub. |
| `/agent-works:memory` | by the agent, or by hand | Use to read project memory before a task, record a lesson, or update status. |
| `/agent-works:orchestrate [the goal, or nothing to resume]` | by the agent, or by hand | Use when the person wants several tasks built, a backlog or a sprint worked, work run in parallel, briefs written for a round of agents, or a round resumed after a restart or a compaction: this session becomes the orchestrator. |
| `/agent-works:resource-locks [run\|acquire\|release\|status] <resource> ...` | by the agent, or by hand | Use before starting anything only one session on this machine can use at a time: a dev-server port, a simulator, a GPU, a shared database, a timing-sensitive test run. |
| `/agent-works:review-card <card id>` | by the agent, or by hand | Use when a child session reports its card in review, by its CARD line, a note from its session, or a board wait waking: check the diff against the done criteria, send findings back, land it on green, close the card. |
| `/agent-works:setup` | by hand | Run to set a repository up for agent work, adopt the agent files it already has, or install the aw launcher. A person starts it. |
| `/agent-works:sync-cards [in-flight\|backlog\|suggested] [card ids]` | by the agent, or by hand | Use when the board may have drifted from the work: a request merged or closed under a card in flight, backlog cards already started or landed, suggestions piling up, the briefing says cards have not changed for a day, or the person asks to sync or groom the board. |
| `/agent-works:work-card <card id>` | by the agent, or by hand | Use when this session was started to work one card from the board, by a brief or by a work-card command naming the card. |

## but-first-planning

Spec, plan, build, as files: author a spec as a browsable docs site, grill and pressure-test it, decompose it into an epic to issue backlog with acceptance criteria, publish it to GitHub or GitLab, and build it issue by issue behind one deterministic status script. Everything lands in .agents/plan/.

Version 5.0.0. [README](../plugins/but-first-planning/README.md), [changelog](../plugins/but-first-planning/CHANGELOG.md).

| Skill | Started | When |
|---|---|---|
| `/but-first-planning:autopilot` | by hand | Runs the whole pipeline hands-off (spec, grill, architect, plan, publish, build, docs) under one up-front contract with one consolidated human gate. Run when the user wants a well-specified project built end to end unwatched. |
| `/but-first-planning:build-assess-drift` | by the agent, or by hand | Triages recorded drift items against the live code: settles what is fixed or by design and opens a routed tracker issue per survivor; it fixes nothing. Use when open drift has piled up, at a sprint boundary, or when asked to triage drift. |
| `/but-first-planning:build-audit` | by hand | Audits a finished plan tree for what the plan missed (unbuilt or unreachable spec promises, onboarding holes, thin tests, missing docs) and turns confirmed gaps into a new epic. Run when a plan tree or an epic is done and a gap audit is wanted. |
| `/but-first-planning:build-improve-architecture` | by the agent, or by hand | Finds deepening refactors in built code (shallow modules, missing seams) and feeds decisions back into the glossary and ADRs. Use when the user asks to find refactors, improve the architecture, or where the seams are. |
| `/but-first-planning:build-next-issue` | by the agent, or by hand | Reconciles plan tree, tracker and git, verifies every done-claim, and reports the next unblocked issue or a parallel dispatch plan; it builds nothing. Use when build work starts or resumes, the user asks what is next, or a done-claim needs checking. |
| `/but-first-planning:build-rubber-duck` | by the agent, or by hand | A thinking partner for a stuck problem: one question at a time, grounded in the code and the spec, changing no file. Use when a bug, an approach, or a confusing piece of code needs talking through. |
| `/but-first-planning:build-sprint` | by the agent, or by hand | Builds a whole sprint from build-next-issue's dispatch plan: a builder subagent per issue, integrated serially on one branch, stopping at human gates. Use when the user asks agents to build a sprint or an epic. |
| `/but-first-planning:build-tdd` | by the agent, or by hand | Builds one plan issue test-first: acceptance criteria become failing tests one at a time, the checkpoint is the gate, the status funnel records the result. Use when implementing a plan issue. |
| `/but-first-planning:build-user-docs` | by the agent, or by hand | Coherence pass over the product's end-user docs (README, `docs/`) for verified sprint work, every command grounded by running it; not the spec site. Use after a sprint verifies, or when asked to document what was built. |
| `/but-first-planning:grill` | by the agent, or by hand | Interview: one question at a time, each with a recommended answer, until intent, done criteria, scope and risks are agreed. Use before planning or building anything not fully specified, before handing work off, and after a round of work to reflect. |
| `/but-first-planning:plan-decompose` | by the agent, or by hand | Decomposes the spec into an epic, sprint, issue tree of vertical slices under `.agents/plan/plan/`, each with acceptance criteria and spec anchors. Use when the spec is settled and the user wants a backlog or a plan. |
| `/but-first-planning:plan-publish` | by the agent, or by hand | Publishes a sprint of the plan tree to GitHub or GitLab, blockers first, and writes each `#NNN` back into the plan. Use when a sprint is about to start or the user asks to publish issues; local-markdown mode publishes nothing. |
| `/but-first-planning:spec-architect` | by the agent, or by hand | Pressure-tests the designed architecture before code exists: shallow modules, leaky seams, deepening candidates in an HTML report, the chosen one grilled into spec edits. Use after spec-grill, or when asked to review the design. |
| `/but-first-planning:spec-edit` | by the agent, or by hand | Changes an existing spec or plan and keeps spec, plan tree and published tickets in step. Use for any change once a spec exists ("the design changed", "add a feature") and to turn inline spec comments into edits. |
| `/but-first-planning:spec-grill` | by the agent, or by hand | Interrogates the spec one question at a time: sharpens the glossary, surfaces contradictions and unstated decisions, records ADRs. Use after spec-write and before planning, or when asked to grill or stress-test the spec. |
| `/but-first-planning:spec-init [--refresh]` | by hand | Scaffolds the `.agents/plan/` workspace: spec site, empty plan tree, glossary and ADRs, tracker config, status scripts. Run once per project, when the user wants to spec or plan it and no workspace exists; `--refresh` updates a workspace's scripts. |
| `/but-first-planning:spec-open` | by hand | Serves the `.agents/plan/` spec site locally (reusing a running server) and opens it in the browser, with inline comments and the live Plan page. Run when the user wants to read, review, or comment on the spec. |
| `/but-first-planning:spec-write` | by the agent, or by hand | Authors or extends the spec as a progressive-disclosure docs site under `.agents/plan/spec/`. Use when the user wants to write or grow a spec ("spec this out", "document the design"). Needs `.agents/plan/`. |

## codebase-optimizer

Staged optimizer for a repository that has already drifted: organize the file tree into AGENTS.md hubs, split god-files behind compatibility shims, and deepen shallow modules. Nothing moves until you have seen the plan, and every stage is validated against the repo's own tests and reverted on red. Detects Python, JS/TS, Go, and Rust; anything else runs generic.

Version 1.0.0. [README](../plugins/codebase-optimizer/README.md), [changelog](../plugins/codebase-optimizer/CHANGELOG.md).

| Skill | Started | When |
|---|---|---|
| `/codebase-optimizer:codebase-organizer` | by the agent, or by hand | Reorganize a sprawling file tree into a progressive-disclosure layout: plan, history-preserving git mv, reference rewriting, AGENTS.md hubs, verified by the repo's own build. Use when the ask is about the tree alone (the root is a mess, too many top-level files, organize the folder structure, add AGENTS.md hubs to this repo). Nothing moves until the person has approved the plan. To split god-files in the same pass use optimize-codebase. |
| `/codebase-optimizer:improve-codebase-architecture` | by the agent, or by hand | Find deepening opportunities in code that already exists: shallow modules, leaky seams, missing adapters, proposed against the project's glossary and its decision records under .agents/. Use when the ask is about architecture ("improve the architecture", consolidate tightly-coupled modules, make this testable) or a seam worth extracting has been spotted. For the file tree use codebase-organizer; to apply deepenings autonomously behind revert on red use optimize-codebase. |
| `/codebase-optimizer:optimize-codebase` | by the agent, or by hand | The whole sweep and the entry point for the other two skills here: organize the tree, split god-files, deepen shallow modules, each stage on a branch behind the repo's own tests with revert on red. Use when the ask is a multi-stage refactor over a repository that has accreted ("optimize this codebase", "decompose these huge files"). Nothing starts until the person has seen the run plan and said yes. For the tree alone use codebase-organizer; for seams alone use improve-codebase-architecture. |

## agentic-teamwork

Team git conventions that hold whoever is typing: session hooks judge every commit and push, a pre-commit hook covers the terminal, and a CI gate backs both, with skills that scaffold a repo, ship and land a change, and keep tests honest. GitHub and GitLab.

Version 1.0.0. [README](../plugins/agentic-teamwork/README.md), [changelog](../plugins/agentic-teamwork/CHANGELOG.md).

| Skill | Started | When |
|---|---|---|
| `/agentic-teamwork:audit-project [--fix]` | by the agent, or by hand | Check the repo you are in against the team conventions: the marker and its version, the hub and its CLAUDE.md link, the ignore block and the CI gate, drift of the repo's scripts and pre-commit hook, the shared permission rules, the lane commands against the package scripts, a strict test gate with nothing to run, a live lane where a model is called, and credentials in the index. Use when the guards or the CI gate seem off, after a plugin update, or when asked to audit or verify the setup. --fix applies the mechanical repairs. To set a repo up in the first place use init-project. |
| `/agentic-teamwork:bootstrap` | by hand | Put a new or not-yet-set-up repo on the team conventions before any code is written in it: three questions, one local run, and the rules, lanes and checks are live for everything written after. Use when the session briefing says the repo is not on the team conventions yet, or when starting a project in an empty folder. Nothing is created on a forge and nothing is pushed. For the full set of options use init-project; to check a repo already set up use audit-project. |
| `/agentic-teamwork:init-project [--upgrade] [--name <n>] [--template library\|node-service] [--forge github\|gitlab\|none] [--strict] [--dry-run]` | by hand | Put a repo on the team conventions: scaffold a new one from a template, or run --upgrade to put the marker, the hub, the CI gate, the permission rules and the pre-commit hook around a repo that already exists, or to bring an earlier scaffold forward. Use when starting a new repo, when the session briefing or audit-project says to run the upgrade, or to turn on the strict test gate with --strict. Local only: it creates nothing on a forge and pushes nothing. To check a repo that is already set up use audit-project. |
| `/agentic-teamwork:land <number> \| --branch <b>` | by the agent, or by hand | Use when a reviewed pull request or merge request should land: its checks are waited on in the background and it is merged on green. Reads the request, waits only on states that resolve by themselves, merges only the head that was reviewed and removes the source branch, then brings the base checkout level; red checks go back to the branch's owner and a missing approval to the person. Also how to merge a stack from the bottom. To open the request in the first place use ship. |
| `/agentic-teamwork:ship [--stack] [--draft]` | by the agent, or by hand | Take finished work from the working tree to an open pull request or merge request: branch if needed, commit with a conventional subject, confirm the tests ran, ask before pushing, and open the change request on the repo's forge. Use when the user says ship it, open a PR, open an MR, or push this. --stack targets the branch below instead of the default branch; --draft opens it as a draft. To merge it afterwards use land. |
| `/agentic-teamwork:tdd` | by the agent, or by hand | Red, green, refactor over this repo's four test lanes (unit, integration, e2e, live), with the lane commands read from the marker rather than guessed. Use when writing or changing tests, when a change needs a failing test first, when wiring a new repo's lanes, or when deciding what to mock and what to run for real. |

## write-like-me

Reshapes how Claude writes human-facing prose — emails, docs, READMEs, posts, chat replies — so it sounds like you instead of like a language model. A calibrated, tightly line-budgeted voice profile auto-loads into every session; skills audit text for AI tells and rebuild the profile; reflective hooks fold your style feedback back in.

Version 1.0.0. [README](../plugins/write-like-me/README.md), [changelog](../plugins/write-like-me/CHANGELOG.md).

| Skill | Started | When |
|---|---|---|
| `/write-like-me:audit` | by the agent, or by hand | Analyze existing text for AI-writing tells, report a verdict, and optionally rewrite it in the user's voice. Use when the user runs /write-like-me:audit, asks "does this sound AI-written?", or wants a draft checked for AI tells. (Fresh prose is the write-like-me skill's job.) |
| `/write-like-me:calibrate` | by hand | Build or rebuild the user's writing voice profile through sample analysis and a short interview. Use when the user runs /write-like-me:calibrate: the plugin's one-time setup, and the full rebuild when the profile has drifted. |
| `/write-like-me:review` | by hand | Show, prune, revert, or configure the user's writing profile and its auto-refinement history. Use when the user runs /write-like-me:review to see what the learning loop changed, undo a revision, or pause learning. |
| `/write-like-me:write-like-me` | by the agent, or by hand | Write human-facing prose in the user's own voice, free of AI tells. Use EVERY time you are about to write or rewrite prose a human will read — emails, docs, READMEs, reports, posts, summaries, chat replies — and whenever the user says "draft", "write up", "humanize", "de-AI", "make it sound like me", or complains that text "sounds like AI". Prose only: code, commit messages, and PR descriptions are out of scope. |

## code-diet

Your agent's code is tomorrow's context: code-diet makes the agent stop at the first rung that works, check what already exists before building, land its cuts one commit at a time behind validate-or-revert, and mark every shortcut with the condition that ends it.

Version 1.0.0. [README](../plugins/code-diet/README.md), [changelog](../plugins/code-diet/CHANGELOG.md).

| Skill | Started | When |
|---|---|---|
| `/code-diet:capture-reusable` | by the agent, or by hand | At the end of a session, find what this work built that another project would want: a component, a repo-agnostic utility, a script, or a pattern worth a plugin. Writes a row in .agents/reuse-opportunities.md for each. Use when wrapping up work that produced something general; reuse-first is the same question pointed the other way. |
| `/code-diet:debt [--write <file>]` | by the agent, or by hand | Inventory every `debt:` marker in the repo with scripts/debt.mjs, judge whether each deferral still holds, and flag trigger-less markers as rot risk. Use when auditing shortcuts already in the tree, before a release, or when the user asks what debt this repo carries; the ladder skill is what writes new markers. |
| `/code-diet:ladder` | by the agent, or by hand | Build at the first rung that holds: YAGNI, reuse what the repo already has, stdlib, native platform, installed dependency, one line, the minimum that works. Use on any coding task (writing, adding, refactoring, fixing, choosing a dependency) and whenever the user asks for the simplest solution or complains about bloat, boilerplate, or over-engineering. To check what already exists before building use reuse-first; to audit shortcuts already in the tree use debt. Not for prose. |
| `/code-diet:reuse-first <the thing, in plain words>` | by the agent, or by hand | Before building a component, a utility, a parser, a client, or anything else that sounds like it might already exist, check what this repo and the other checkouts the person has listed already have. Use whenever a task would add a dependency, a UI component, or a capability another module plausibly has, and whenever the ladder reaches rung 2. To offer something back the other way use capture-reusable. |
| `/code-diet:review-diet [repo] [--base <ref>] [--apply]` | by the agent, or by hand | Hunt over-engineering in the working diff (pass `repo` to widen to the whole tree): review-scan.mjs locates cut candidates deterministically, you judge only the flagged spots, one line per finding with file:line, the cut, and the replacement; `--apply` lands each confirmed cut as its own commit behind validate-or-revert. Use before opening a pull or merge request, or when a diff feels bloated. Correctness bugs and security holes are out of scope here; the ladder is what stops the bloat being written in the first place. |

## plugin-workbench

A plugin's real cost is invisible until installed, and authoring one means guessing at unwritten standards, so make, measure, and fix plugins around one six-dimension rubric: scaffold and author against it, score any plugin into an HTML scorecard with an adopt or rework verdict, apply the fixes ranked by the point delta a script computes, read back what each plugin put in a session's context, and reinstall a marketplace checkout from the working tree.

Version 1.0.0. [README](../plugins/plugin-workbench/README.md), [changelog](../plugins/plugin-workbench/CHANGELOG.md).

| Skill | Started | When |
|---|---|---|
| `/plugin-workbench:context-lens [report\|serve] [session id or transcript path]` | by the agent, or by hand | Show what entered an agent's context window, when, and from which plugin, read from the Claude Code session transcript: each hook's output by event and who saw it (the model, the person, or nobody), the CLAUDE.md and .agents rule imports, the skill listing per plugin, the API's own token count per request, and what each compaction kept or lost. Use when checking that a plugin's hooks inject what they should, sizing a briefing, checking what survives compaction, or when the person asks what the agent actually saw. |
| `/plugin-workbench:create-plugin <plugin idea \| existing dir to wrap> [--dir <parent>] [--bar <composite>]` | by the agent, or by hand | Author a new plugin end to end: interview for intent, scaffold the layout with a script, write the skills against the evaluation rubric, then score and fix until the verdict is adopt. Use when someone wants to make a plugin, turn existing skills or scripts into one, or asks what a good plugin needs. |
| `/plugin-workbench:evaluate-plugin <path \| owner/repo \| git URL>[#ref] [--output <dir>]` | by hand | Score a plugin against the six-dimension rubric (skill quality, component symbiosis, workflow quality, architecture, context-window footprint, distribution hygiene) into a chat summary, a markdown report, and an HTML scorecard with an adopt, adopt-with-fixes, rework, or avoid verdict. Use when someone wants a plugin or a bare skill directory evaluated, audited, or compared before installing it. |
| `/plugin-workbench:improve-plugin <path \| owner/repo \| git URL>[#ref] [--report <dir with score.json + grades.json>] [--bar <tier \| composite>] [--output <dir>]` | by the agent, or by hand | Raise an existing plugin's score: baseline it or reuse a prior scorecard, rank the fixes by the point delta the scanner computes, apply them, re-score, and report before against after. Use when someone wants a plugin improved, scorecard findings fixed, or a score pushed past a verdict tier. |
| `/plugin-workbench:refresh-marketplace [--plugins a,b] [--dry-run]` | by hand | Validate a marketplace checkout and reinstall its plugins from the working tree, so the edits made this session are what the next session loads. Use when someone has changed a plugin in a marketplace checkout and asks to refresh, reinstall, or try it. |

## perceptual-loop

An agent can't iterate on what it can't measure: perceptual-loop turns image, video and audio work into reproducible shots, numbers that gate a candidate against its own accepted run, sheets the agent and you can look at, a blind critic, a render budget, and one review page for the judgements only a person should make, in Node with ffmpeg as the one external tool.

Version 1.0.0. [README](../plugins/perceptual-loop/README.md), [changelog](../plugins/perceptual-loop/CHANGELOG.md).

| Skill | Started | When |
|---|---|---|
| `/perceptual-loop:calibrate-gate` | by the agent, or by hand | Use when a perceptual gate fails on something untouched, numbers wobble between identical runs, or a baseline is about to be accepted. Measures noise into tolerances. |
| `/perceptual-loop:check-audio` | by the agent, or by hand | Use when a task produces or changes sound, or sound must stay in sync with a picture. Measures loudness, silence and clipping, pitch, onsets, lag, spectra, and draws spectrograms. |
| `/perceptual-loop:check-motion` | by the agent, or by hand | Use for animation, transitions, smoothness, latency, or any clip, where a still cannot show it. Measures over time: jumps, flicker, judder, flow direction, clip against clip, contact sheets. |
| `/perceptual-loop:define-success <task in a sentence>` | by the agent, or by hand | Use before changing how something looks, moves, or sounds, or when a brief only says make it look right. Writes the success file naming what will prove the change. |
| `/perceptual-loop:iterate-shots <shot> [<shot> <shot>] \| --group <g> --match <glob>` | by the agent, or by hand | Use for every change and check on a picture or render, and when tempted to run the whole suite: a few proving shots, before and after, the gate. |
| `/perceptual-loop:judge-and-queue` | by the agent, or by hand | Use when a difference in a picture needs a verdict, a finished look change needs a blind second look, or taste questions wait for the owner: one review page. |
| `/perceptual-loop:perceptual-loop` | by the agent, or by hand | Use at the start of work judged by eye or ear: a render, an image, an animation, or a sound. Routes to the skill for each step. |
| `/perceptual-loop:probe-the-source` | by the agent, or by hand | Use when a colour, brightness, shape, or timing differs from the reference and the cause is unknown, or before implementing a rule guessed from pictures. |
| `/perceptual-loop:shot-harness [what the project renders, and what the reference is]` | by hand | Use to set a project up for perceptual checks: the state folder, the render commands, shots, helper passes, groups, and the render budget. The person starts it. |

## docs-parity

User docs drift because they ship after the code, so docs-parity makes them move in the same change: a writer contract with audiences and a page shape, screenshots made only by a deterministic capture harness for any stack, one checker that maps code to pages and finds missing, stale and broken docs in session and in CI, and a README check that keeps the front page written for people.

Version 1.0.0. [README](../plugins/docs-parity/README.md), [changelog](../plugins/docs-parity/CHANGELOG.md).

| Skill | Started | When |
|---|---|---|
| `/docs-parity:docs-audit [root or page glob to limit the audit]` | by the agent, or by hand | Audit the whole user-docs set against the product: the checker's tree and stale modes plus a read of every page against the code, reported as findings with fixes. Report only; edits nothing. Use before a release, after a large change to a user-visible surface, or when the user asks whether the docs are current; to fix what it finds use docs-sync. |
| `/docs-parity:docs-init [target: site \| docs-folder \| wiki \| readme] [audiences]` | by hand | Adopt docs-parity in a repo: detect the stack and the docs target, then write .agents/docs-parity.json (with a first code-to-docs surface map) and the writer contract .agents/docs-contract.md. Use when a repo with user docs should get the docs rule in every session, the Stop check, and the checker in CI. |
| `/docs-parity:docs-parity` | by the agent, or by hand | Keep user-facing documentation in the same change as the code it describes: pages, screenshots, and the nav move with the commit that changes a screen, label, flow, command, flag, config key, endpoint, permission, error message, or install/deploy step. Use whenever an edit touches something a user, integrator, or operator sees or depends on, when the user says "update the docs", "document this", "add a screenshot", "retake the screenshots", or "are the docs current", and when unsure which docs skill fits. Works for any stack and any docs target (a site, a docs/ folder, a wiki, a README). |
| `/docs-parity:docs-shots` | by the agent, or by hand | Build, extend, or repair the project's documentation screenshot harness so every docs image is captured deterministically from the built product, never by hand: light and dark pairs, a fictional cast, pinned clock and seeds, cropped not scaled. Use when a page needs a new screenshot, a shot is stale or flaky, a project has no capture harness yet, or the user asks to "add a screenshot", "retake the screenshots", or "set up screenshot capture" for a web app, desktop app, CLI, game engine (Unreal), notebook, or mobile app. |
| `/docs-parity:docs-sync` | by the agent, or by hand | Bring the user docs level with a code change before it is committed: map the diff to the pages and screenshots it affects, rewrite those pages, retake the affected capture groups, run the checker, and write the Docs: line. Use after (or while) changing a user-visible surface, when the Stop hook or CI reports PARITY_MISSING or SHOT_STALE, or when the user says "update the docs for this", "sync the docs", or "retake the screenshots". |
| `/docs-parity:readme` | by the agent, or by hand | Rewrite a README so it tells a person what the project is, why to use it, and how, in at most 800 words and standard-readme's section order, and move everything else to its proper home (CONTRIBUTING.md, docs/, AGENTS.md, CHANGELOG.md). Use when readme-check.mjs, the Stop hook, or CI reports a readme-* finding or warning, when a README is over the limit, and when writing or reviewing a README. |

## marvelous-miro

Diagrams that stay true: a system map extracted from @system annotations in the code and checked against the real import graph, drawn on a Miro board by generators, with a legibility lint before anything is published, a live check of what Miro actually drew, and board layout pulled back into the repo.

Version 0.1.0. [README](../plugins/marvelous-miro/README.md), [changelog](../plugins/marvelous-miro/CHANGELOG.md).

| Skill | Started | When |
|---|---|---|
| `/marvelous-miro:browser-setup` | by hand | Set up the browser the live Miro check drives (chrome-devtools MCP plus Google Chrome, signed in to Miro) in Claude Code, the Claude Desktop Code tab, or Cowork. Use when the miro-board skill's live check has no evaluate_script or list_pages tool, when the marvelous-miro session note says the check cannot run on this machine, when the Miro tab cannot be found or reached, or to repair the browser for Miro. |
| `/marvelous-miro:diagrams-init [board name or URL]` | by hand | Set a repo up with a system map generated from its code: propose @system annotations from the import graph, write .agents/system-map.json and the committed diagrams/system-map.json, record the Miro board, publish the first frame, and on request copy the checker in for CI. Use when a repo should get a diagram that is extracted from its code and checked against it, once per repo. |
| `/marvelous-miro:diagrams-sync` | by the agent, or by hand | Bring the system map and its Miro board level with a code change: fix the @system annotations, regenerate diagrams/system-map.json, and republish the board. Use when adding a module or a call between modules in a repo that carries .agents/system-map.json, when the checker or CI reports MAP_STALE, MAP_MISSING, UNDECLARED_IMPORT, UNDECLARED_RUN, or BOARD_BEHIND, or when the user says "update the diagram", "sync the board", or "redraw the system map". Also the whole-repo sweep, which assesses every module's annotations against its code: use it when asked to re-annotate the codebase or audit the map. |
| `/marvelous-miro:miro-board` | by the agent, or by hand | Draw a Miro board from code and keep it legible, with a lint before publishing and a live check after. Use when drawing or updating a diagram, flow, or architecture frame on Miro. Also use when a project has a miro.config.mjs, when a board has overlapping cards, crossed or diagonal connectors, or text that does not fit, or when layout changes made in Miro need to reach the repo. |
